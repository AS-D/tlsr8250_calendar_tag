# calendar_tag —— 日历价签固件（走时 + BLE 对时）

在盒马 TLSR8250 价签上显示**当月月历**，并且：

- **不断电就会走**：每秒一次 tick，日期跨天时自己重排（是否顺便刷屏可配）
- **走得准**：时钟源是板上那颗 24MHz 晶振，典型 ±20ppm ≈ **每天 1~2 秒**
- **可手动对时**：手机用 nRF Connect 写 5 个字节即可校准
- **时间只在 RAM**：上电起点是编译时刻，对时后从新值开始走；断电重启回到编译时刻，要准再对一次
- **省电默认**：上电不刷屏、不闪灯；对时后刷一次，之后每天跨天再刷一次（见 3.2）

## 一、日期显示效果

![预览](out/calendar_preview.png)

**横向 250×122**，和盒马原厂同一版式：

- 表头：日 / 六 红底，一~五 黑底，白字
- 7 列 × 6 行日期，周末数字红色，**今天红块白字**
- 右侧信息栏（**整体居中、不画外框**）：**年份（红）**、干支生肖（黑小字）、**公历月（红）**、**农历日期（黑小字）**、第几周

面板物理上是竖屏，所以绘制用横向坐标、每个像素经 `lpx()` 旋转 90° 写入显存。
**把价签横过来**（FPC 朝左）就是正常阅读方向。

若装上发现方向反了（要往另一头转才正），把 `src/calendar.c` 里的 `CAL_ROT` 改成 1。

### 字体（2026-11-19 重做，替换原来的自制字模）

原来的字形是 `tools/gen_fonts.py` 从 TTF 转的 8×14 / 12×12 定点字模，问题很直观：
**一/二/三 变成粗横杠**（12×12 里横画只有 1px，放大后就是三根杠）、数字带**双描边**、
比例全靠"每字固定宽度"硬凑，所以居中也歪。

现在全部改用 **u8g2 点阵字体**，字体数据来自 `ink-tag-da14585` 工程
（那套固件同款、已在同类墨水屏价签上跑过）：

| 字体 | 像素高 | 用在哪 |
|---|---|---|
| `u8g2_font_wqy9_t_lunar` | 12px | 干支生肖、农历、周（文泉驿点阵宋 Bold） |
| `u8g2_font_wqy12_t_lunar` | 16px | 表头 日一二三四五六、公历月的"月"（同上，加粗靠 1px 叠印） |
| `u8g2_font_helvB14_tn` | 14px | 日期数字、周数数字（Helvetica Bold） |
| `u8g2_font_helvB18_tn` | 18px | 年份 2026、公历月数字（Helvetica Bold，红字） |

- 数据在 `src/font_u8g2.c`（约 9.6KB，可用 `python tools/extract_u8g2_fonts.py` 从参考工程重新生成）
- 解码/绘制是 `src/u8g2_font.c/.h`（U8g2_for_Adafruit_GFX 的精简移植，唯一出口是
  `draw_hv_line()` 回调，这里把它接到 `lpx()`，所以字体也是转 90° 画进竖屏显存的）
- u8g2 的 `DrawStr` 只认单字节，中文得自己解 UTF-8 再逐个 `DrawGlyph()`（见 `utf8_next()`）
- 换成比例字宽后，居中改成**按实测字宽算**（`text_w()`），不再"每字 12px"累加
- 只有 16px 的"月"做 1px 叠印加粗（跟 18px 的月数字配平）；表头和 12px 中文都**不**加粗——
  实测表头加粗会把"四/五"的小窗糊死，12px 的"周/十"也会糊成一坨

> 字体版权：文泉驿点阵宋（GPL + 字体嵌入例外）、Adobe Helvetica Bold 点阵（u8g2 自带），
> 自用没问题；要商用请先确认这两份字体的授权。

### 农历

`src/lunar_table.h` 是 1900–2100 的置闰表（201 项），由 `tools/gen_lunar.py` 生成。
生成前会**自动校验**：12 个已知春节必须都是正月初一、4 个中秋必须都是八月十五，
校验不通过就拒绝生成——所以这张表不是抄来就用的。

换算算法在 `src/lunar.c`：以 1900-01-31（正月初一）为基准，先按农历年长度扣减、
再按农历月长度扣减（闰月插在对应月份之后）。

农历日期按 UTF-8 拼成"闰六月初八"这种整串再整串居中，不再逐个字形摆位置；
干支/生肖按**农历年**推（甲子起于公元 4 年），所以跨年、闰月都不会显示错干支。

实测校验：`2026-07-19` → **六月初六**，和原厂价签上显示的完全一致。

### 不做电量显示（这块板没必要）

2 节 CR2450 并联，标称 3.0V、内阻小、放电平台极平：从满电一直到 2.7V 之前，
读数基本趴在 3.0V 不动。屏上画个固定不动的"3.0V"，没有任何信息量，还白占右栏空间。

所以工程里**没有电量代码**：不读 ADC、没有电池图标，右栏就是三段
`年份 + 干支` / `公历月 + 农历` / `周数`。

真要判断电池快没电，看的是**带载压降**：刷新那 20 秒把万用表挂在电池两端，
掉到 2.4V 以下就该换电池 —— 这比任何静态读数都可靠。


## 二、走时是怎么算的

```
起点  = BUILD_EPOCH（build.ps1 在编译时写入的 Unix 时间戳）
走时  = clock_time() 差值累加（系统定时器 16 tick/µs = 16MHz）
显示  = (epoch + 8 小时) 换算成年月日
```

- **上电后时间冻结**：`app_time_init()` 只记起点，`app_time_tick()` 里有个"对时过没有"的开关，
  没对时过就直接返回 0 —— 不加秒、不判跨天、不刷屏。**只有手机对时之后，时间才开始走**。
- 时间基准统一用 **UTC Unix 秒**，显示时才加 `CAL_TZ_OFFSET`
- **跨天判断也按当地日期**：`(epoch + TZ) / 86400`，所以是北京时间 0 点跨天，
  不是 UTC 0 点（UTC 0 点对应北京时间早上 8 点）。显示和逻辑用的是**同一个时区值**，
  不会出现"屏上已经 1 号、固件还认为在 31 号"的错位。
- 32 位 tick 约 268 秒回绕一次，代码用无符号减法处理
- 每次刷屏会阻塞约 20 秒，这期间的 tick 不会丢——`app_time_tick()` 是用差值累加的
- 只有对时过之后才会判"跨天"，所以不会出现"没对时也每天自己重画"

改时区：`src/app_cfg.h` 里的 `CFG_TZ_HOURS`（默认 8）。改这一处，
**日历显示和跨天刷新会一起跟着变**（`calendar.h` 的 `CAL_TZ_OFFSET` 就是由它算出来的）。

### 3.2 省电默认长什么样

出厂默认（`CFG_BOOT_REFRESH 0` / `CFG_LED_DEBUG 0` / `CFG_DAY_REFRESH 1`）的行为：

| 时刻 | 动作 |
|---|---|
| 上电 | 只把屏的引脚设成确定电平；广播 + 等对时，**时间冻结在编译时刻不走秒**，一个像素都不刷 |
| 手机对时 | 收到 5 字节 → 主循环里设时间（**从此开始走时**）→ 初始化屏 → 画月历 → 刷一次（~20 秒）|
| 跨天 | **只有对时过之后才判**：**北京时间**跨过 0 点 → 重画并刷一次，保证“今天”的红块跟着日期走 |
| 空闲 | LL 进 suspend，每个广播间隔（200ms）醒一次发一包 |

省电与正确性的取舍就在这里：**跨天刷一次是三色全刷，约 20 秒**，这是让“今天”跟着走的代价。
真在意续航就把 `CFG_DAY_REFRESH` 改 0——那时只在手机对时后刷，屏上高亮会停在最后一次刷屏那天。

另外**任何时间都不写 flash**：没有存档，就没有擦扇区的开销，也没有低电压写坏扇区的风险。

当前默认 `CFG_ADV_INTERVAL` 已是 320（200ms），平均待机电流约 0.065mA，
按 2 节 CR2450 并联（可用 ~1020mAh）估算约 1.8 年。想更快被发现改 160（100ms，约 14 个月），
想更省改 480（300ms）。

## 四、BLE 手动对时（不用拆机、不用烧录）

原理：价签广播，手机连上后往 SPP 的 Client2Server 特征值写 5 个字节，
固件收到就把时间设成那 5 字节里的值，然后立刻重画一次。

> **广播现在是本工程自己开的**（`src/ble_app.c`：`blc_ll_setAdvData` + `blc_ll_setAdvEnable`），
> 名字 `calendar_tag`、flags `0x06`（General Discoverable）。
> 早先"手机搜不到"的根因是 SDK demo 的 `app.c` 里有一句
> `blc_ll_setAdvEnable(BLC_ADV_DISABLE)`（注释写着"BMS 只做主机，不广播"）——
> 那个文件现在已经不参与编译了，所以这个坑从结构上消失了。

### 4.1 参数（一次记牢）

| 项 | 值 |
|---|---|
| 广播名 | **`calendar_tag`**（本工程自己设的，12 字符） |
| 特征值（写） | **`00010203-0405-0607-0809-0a0b0c0d2b11`**（S2C 是 `...2b10`，只用于 notify，不用管） |
| 通道属性 | read + **write without response** |
| 一次写入长度 | **5 字节**（少一个字节固件就整条丢弃） |

### 4.2 手机：nRF Connect（最省事，推荐）

1. 手机装 **nRF Connect for Mobile**（安卓/iOS 都有，免费）
2. 打开扫描，找到 **`calendar_tag`** → `CONNECT`
   （若弹配对请求，直接取消即可，这个特征不要求加密）
3. 展开服务，找到特征 **`00010203-...-2b11`**，点右侧的向上箭头（Write）
4. Write type 选 **Without response**，数据格式选 **Byte Array**，填入 5 个字节
5. 点 **SEND / OK** —— 屏会刷一次，大约 15~20 秒后出新画面

### 4.5 怎么确认真的对上了

- 屏上**今天的高亮块**会跳到新日期；跨月、跨年会整页重排（年份/月/农历/干支一起变）。
- 想看得更明显：先写一个**明天**的时间（高亮块挪一格），确认生效后再写回当前时间。
- 写入后屏会刷一次（约 15~20 秒）；默认不闪灯。

### 4.6 几个坑

- **写进去之后连接会掉**：刷屏那 20 秒是阻塞式忙等，BLE 停摆，手机看到"断开"是正常的，
  不要以为失败又重写一遍——重写会再刷一次屏，白费电。
- **只认 5 字节、首字节必须是 0x01**；长度不足或命令码不对会被整条丢掉（`src/ble_app.c` 的 `on_ts_write()` 里 `if (len < 5 || v[0] != 0x01) return 0;`）。
- **不会接受明显非法的年份**：`app_on_time_from_ble()` 里 `epoch < 1600000000`
  （2020-09-13 之前）直接忽略，防止写进一个 1970 年的时间。
- 对时结果**只存在 RAM**（不写 flash，见 4.8）：断电/换电池就回到编译时刻，
  上电后要再对一次时。要断电也准，只能加 RTC 芯片（DS3231 类 + 纽扣电池）。
- **别在刷屏那 20 秒里写**：广播是链路层硬件按间隔自己发的（主循环阻塞也照发，刷屏时也扫得到），
  但 ATT 写请求要等主循环回来才处理——刷屏中途写会被拖到刷完才生效，连接多半已超时。
  等屏刷完再写最稳。
- 广播是主要功耗来源。`src/app_cfg.h` 的 `CFG_ADV_INTERVAL` 已设为 320（200ms）
  调到 320（200ms）；不需要随时可连的话，也可以只在需要时调 `ble_app_adv(1)`。

### 4.7 协议

| 字节 | 含义 |
|---|---|
| `[0]` | `0x01` 命令码：设置时间 |
| `[1..4]` | Unix 时间戳，**小端 32 位**（UTC 秒，即北京时间 − 8 小时） |

实现位置：`src/ble_app.c` 的 `on_ts_write()`（挂在对时特征的写回调上），
收到后交给 `app.c` 的 `app_on_time_from_ble()`，主循环里再设时间 + 刷屏。

## 六、已知限制
- **断电就回到编译时刻**：时间只在 RAM、不落 flash，上电从 `BUILD_EPOCH` 起步。
  要断电也准，只能加 DS3231 这类 I2C RTC + 纽扣电池。
- **刷屏那 ~20 秒 BLE 会断**：`display_present()` 是阻塞的，链路层靠中断维持但上层不动。
  对时数据在刷屏前已经收完并落盘，所以断开不影响结果，只是手机端会看到连接断开。
- **`CFG_DAY_REFRESH 0` 时高亮不动**：见 3.2 的取舍说明。
